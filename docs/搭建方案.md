## 1. 为什么选 Astro 而不是 Hexo / Next.js

「OI 大佬的个人网站」这个品类的技术特征很明确：**内容为主 + 动效密集 + 首屏要快**。

| 维度 | Astro 7 | Hexo + Butterfly | Next.js 15 | Hugo |
| --- | --- | --- | --- | --- |
| 首屏 JS | **~9 KB**（零 JS 默认） | 中等（主题注入全局脚本） | ~463 KB | ~5 KB |
| 内容模型 | Content Collections（类型安全 schema） | `_posts/` 约定 | 需自建 | 内容目录约定 |
| 动效自由度 | **完全自有**（组件级） | 受限于主题 EJS 注入 | 完全自有 | 受模板限制 |
| 岛屿架构 | ✅ 按需水合 | ❌ | ✅ | ❌ |
| 构建速度 | Vite 8 + Rolldown，38 页 4.2s | 几百篇 1min+ | 中等 | 最快 |
| 上手门槛 | 中 | 低 | 中 | 低 |
| Live2D 集成 | 岛屿内按需加载 | 靠 hexo-helper 插件 | 简单 | 需模板改造 |

**关键决策**：OI 圈现成方案（Hexo + Butterfly）确实上手快，但两个问题会在半年后爆发：

1. **主题绑定太深** —— 想改一个动效要去翻主题目录的 EJS 模板和注入插件；
2. **动效层全是全局注入** —— Butterfly 靠 `inject` 把 JS 塞进每一页，页面一多加载开销就上来了。

Astro 的取舍正好相反：内容层极干净（就是一堆 `.md`），动效层全部是自己的组件。

> **给 OI 圈的一句实话**：如果你只是想要「一个好看的博客」且不打算改，Hexo + Butterfly 五分钟就能上线；
> 但如果你想「做出自己的风格」，Astro 的天花板高得多——因为所有视觉层都是你写的。

## 4. 视觉设计系统

### 4.0 设计语言来源：从「参考站」反推设计 DNA

这一版视觉不是拍脑袋设计的，而是**从参考站反推出的设计 DNA**。
方法：用 Playwright 抓取参考站的截图 + 主题 CSS，提取计算样式与具体规则。

```js
// scripts/capture-ref2.mjs —— 提取参考站的设计参数
const detail = await page.evaluate(() => {
  const g = (el, p) => (el ? getComputedStyle(el)[p] : null);
  return {
    bodyFont: g(document.body, 'fontFamily'),   // "Maple Mono NF CN", ...
    bodyFontSize: g(document.body, 'fontSize'),  // 12px
    mainWidth: document.querySelector('#blogColumn')?.getBoundingClientRect().width, // 950
  };
});
```

再下载主题 CSS 直接读源码规则（`bundle-simplememory.min.css`）：

```bash
curl -s https://www.cnblogs.com/skins/simplememory/bundle-simplememory.min.css -o sm.css
# 提取 .postTitle 的原始定义
grep -o '\.postTitle[^{]*{[^}]*}' sm.css
```

**反推出的核心参数**：

| 元素 | 参考站原始定义 | 含义 |
| --- | --- | --- |
| 主色 | `#21759b`（出现 24 次） | 深青蓝，非通用蓝 |
| 正文色 | `#333` / 次要 `#757575` | 双层灰阶 |
| 分割线 | `#ededed` / `#e6e6e6` | 极细，比常规再淡一档 |
| 正文 | `font-size: 14px; line-height: 1.8; text-indent: 2em` | **首行缩进 2em** |
| 标题 | `.postTitle { border-left: 3px solid #21759b; font-size: 20px; float: right }` | **左竖线 + 20px 不加粗** |
| 日期徽章 | `.dayTitle { border: 1px solid #21759b; border-radius: 50%; width: 63px; height: 65px; margin-left: -100px }` | **圆形徽章浮在左侧** |
| 元信息 | `.postDesc { font-size: 13px; color: #757575; padding-left: 20px }` | 左侧留图标位 |
| 滚动条 | 3px | 极窄 |

> **这条经验值得单独记住**：拿到一个设计参考时，不要靠肉眼"感觉像"，
> 要**抓 computed style + 下载主题 CSS**，把"感觉"变成可复现的具体数值。
> 否则做出来的只是"类似"，永远对不上。

### 4.1 色彩：等宽极简的青蓝体系

```css
@theme {
  --color-primary: #21759b;        /* 主色 · 青蓝 */
  --color-primary-light: #3671a5;
  --color-primary-dark: #0f3647;
  --color-accent: #807dd4;         /* 强调紫 */
  --color-code: #d83b64;           /* 行内代码玫红 */
  --color-code-bg: #f9f2f4;
  --color-line: #ededed;           /* 分割线 */
  --color-ink: #333;               /* 正文 */
  --color-ink-strong: #3a4145;     /* 标题 */
  --color-ink-mute: #757575;       /* 次要文字 */
}
```

设计要点：

- **主色不做渐变**。参考站从头到尾只有一个青蓝，渐变是"现代 SaaS 风"的标志；
- **双层灰阶**（`#333` 正文 / `#757575` 次要）比单一灰度更有层次；
- **分割线要淡到"几乎看不见但删掉就散架"** —— 这是极简风的关键。

### 4.2 主题切换：亮色 / 暗色

```css
:root {
  --bg: #fff;
  --bg-soft: #fbfbfb;
  --fg: var(--color-ink);
  --fg-strong: var(--color-ink-strong);
  --fg-mute: var(--color-ink-mute);
  --border: var(--color-line);
  --border-soft: var(--color-line-soft);
  --link: var(--color-primary);
}
html.dark {
  --bg: #1a1c1f;
  --bg-soft: #222529;
  --fg: #c8ccd0;
  --fg-strong: #e6e9ec;
  --fg-mute: #7d858c;
  --border: #33383d;
  --border-soft: #2a2e33;
  --link: #7fb0e0;
}
```

**防闪烁**：主题脚本必须内联在 `<head>` 里、样式应用之前执行。
放在 `<body>` 末尾会导致暗色用户看到一瞬间的白屏。

```html
<script is:inline>
  (function () {
    try {
      var saved = localStorage.getItem('theme');
      var prefersDark = matchMedia('(prefers-color-scheme: dark)').matches;
      if (saved === 'dark' || (!saved && prefersDark)) {
        document.documentElement.classList.add('dark');
      }
    } catch (e) {}
  })();
</script>
```

### 4.3 字体：Maple Mono 等宽中文

参考站全站使用 **Maple Mono NF CN**（等宽），中文也是等宽 —— 这是它最有辨识度的地方。

```css
@theme {
  --font-sans: 'Maple Mono', 'Maple Mono NF CN', 'Maple Mono SC NF',
                Merriweather, 'Open Sans', system-ui, sans-serif;
  --font-mono: 'Maple Mono', 'Maple Mono NF CN', 'JetBrains Mono',
                Ubuntu Mono, Menlo, Consolas, monospace;
}
```

**基准字号体系**：参考站 `body { font-size: 12px }`，配合 `html { font-size: 62.5% }`，
于是 `1rem = 10px`，所有尺寸都能写成 `1.4rem` 这样的紧凑值。

```css
html { font-size: 62.5%; }   /* 1rem = 10px */
body { font-size: 12px; line-height: 1.7em; }
```

**字重分配（极简风的关键）**：

| 场景 | 字重 | 说明 |
| --- | --- | --- |
| 文章标题 | **400** | 参考站标题不加粗，靠左竖线建立层级 |
| 正文 | 400 | |
| 区块标题 | 400 | 靠字号 + 分割线建立层级 |
| 导航当前项 | 700 | 全站唯一的强调粗体 |

> 极简风和"到处加粗"的现代风格完全相反：
> 层级靠**字号、颜色、留白、线条**建立，而不是靠字重。

**字重与行高建议**：

| 场景 | 字号 | 行高 |
| --- | --- | --- |
| 文章标题 | 2rem (20px) | 1.5 |
| 正文 | 1.4rem (14px) | 1.8 + **首行缩进 2em** |
| 摘要 / 元信息 | 1.3rem (13px) | 1.85 |
| 标签 / 代码 | 1.15-1.3rem | 1.6-1.75 |

> **字体加载策略**：Maple Mono 完整版 **152 MB**，必须子集化。
> 用 `fonttools` 实例化字重 + 按站点实际用字裁剪：

```python
# scripts/subset-font.py
from fontTools import varLib
from fontTools.varLib import instancer
from fontTools import subset

# 可变字体 → 实例化 wght=400 / 700
font = varLib.load(font_path)
instancer.instantiateVariableFont(font, {"wght": 400})
subsetter = subset.Subsetter()
subsetter.populate(text="".join(all_chars))   # 扫描 src/ 与 public/ 收集用字
subsetter.subset(font)
```

实测结果：**152 MB → 31 KB (400) / 32 KB (700)**，配合 `font-display: swap` 与 `<link rel="preload">`。

### 4.4 标志性组件：三个"简单但难做对"的元素

**① 标题左竖线** —— 参考站 `.postTitle` 的灵魂

**② 圆形日期徽章** —— 浮在文章流左侧

```css
.day-badge {
  position: absolute;
  top: -1.5rem;
  left: -7rem;
  width: 6.3rem;
  height: 6.5rem;
```

**③ 正文首行缩进 2em** —— 中文博客的"书卷气"

```css
.prose p { text-indent: 2em; text-align: justify; }

.prose p:has(> img), .prose p:has(> pre),
.prose p:has(> .katex), .prose p:has(> table) { text-indent: 0; }
```

### 4.6 迁移旧设计的正确姿势

改视觉语言时，最容易犯的错是"只改首页"。旧变量名残留在其它页面里，
浏览器会回退成无效值，整站视觉碎裂。

**三步法**：

1. **先加兼容别名层** —— 在 `:root` 里把旧变量映射到新令牌，保证漏改也不崩：

```css
:root {
  --fg-base: var(--fg);
  --fg-muted: var(--fg-mute);
  --bg-elevated: var(--bg-soft);
  --color-brand-500: var(--color-primary);
  --radius-card: var(--radius-md);
  --shadow-soft: 0 2px 10px -6px rgba(58, 65, 69, 0.25);
  /* ... */
}
```

2. **再逐个重写组件** —— 卡片、标签、按钮都要去掉玻璃拟态与渐变；
3. **最后删掉别名层** —— 确认没有引用后清理。

> 这层兼容别名是"安全网"，不是"终点"。
> 留着它 = 永远有人在用旧设计语言写新页面。

## 5. 动效体系（12 项）

全部手写，**不引入 GSAP / Framer Motion**。理由：博客的动效只需「提示层级」和「提供空间感」，
原生 CSS transition + IntersectionObserver 足够覆盖 90% 场景，少一个依赖首屏少几十 KB。

| # | 动效 | 实现方式 | 触发 | 性能影响 |
| --- | --- | --- | --- | --- |
| 1 | **滚动揭示** | `IntersectionObserver` + `.reveal` 类 | 进入视口 | 一次性 |
| 2 | **卡片 3D 倾斜** | `pointermove` + `perspective(900px)` | 桌面端悬停 | 持续（仅 hover） |
| 3 | **阅读进度条** | `scroll` + `width`（rAF 节流） | 滚动 | 极低 |
| 4 | **数字滚动** | `IntersectionObserver` + rAF + 缓出 | 进入视口 | 一次性 |
| 5 | **打字机 Hero** | `setTimeout` 字符推进 | 页面加载 | 极低 |
| 6 | **视图过渡** | View Transitions API | 页面跳转 | 极低 |
| 7 | **极光背景** | 3 个 CSS blob + `blur(70px)` | 常驻 | GPU 合成 |
| 8 | **粒子网络** | Canvas 2D + 鼠标斥力 | 常驻 | 中（可降级） |
| 9 | **背景缓慢漂移** | CSS `scale(1.02→1.08)` 40s | 常驻 | GPU 合成 |
| 10 | **代码复制按钮** | 悬停显示 + Clipboard API | 悬停 | 一次性 |
| 11 | **TOC 高亮** | `IntersectionObserver` | 滚动 | 极低 |
| 12 | **Toast/气泡** | Live2D 气泡 + 缓动 | 随机/交互 | 极低 |

### 5.1 滚动揭示：错峰延迟

```js
document.querySelectorAll('.reveal').forEach((el, i) => {
  el.style.transitionDelay = `${Math.min(i % 8, 7) * 60}ms`;
  observer.observe(el);
});
```

`i % 8` 是关键 —— 不做错峰的话所有元素同时浮现，反而失去「层次感」。

### 5.2 卡片 3D 倾斜：只给精细指针设备

```js
if (matchMedia('(pointer: fine)').matches) {
  document.querySelectorAll('[data-tilt]').forEach((card) => {
    card.addEventListener('pointermove', (e) => {
      const r = card.getBoundingClientRect();
      const x = (e.clientX - r.left) / r.width - 0.5;
      const y = (e.clientY - r.top) / r.height - 0.5;
      card.style.transform =
        `perspective(900px) rotateX(${-y * 6}deg) rotateY(${x * 6}deg) translateY(-4px)`;
    });
    card.addEventListener('pointerleave', () => { card.style.transform = ''; });
  });
}
```

`pointer: fine` 判断很关键 —— 触屏设备上 `pointermove` 会在滚动时疯狂触发。

### 5.3 粒子网络：鼠标斥力

后台常驻动画最容易拖垮低端机。三条优化：

1. **限制监听范围** —— 不在整个 viewport 监听 `mousemove`；
2. **页面隐藏时停 rAF** —— `visibilitychange` 里 `cancelAnimationFrame`；
3. **密度分档** —— `low` 26 个 / `medium` 48 个 / `high` 80 个粒子。

### 5.4 尊重 `prefers-reduced-motion`

```css
@media (prefers-reduced-motion: reduce) {
  *, *::before, *::after {
    animation-duration: 0.01ms !important;
    animation-iteration-count: 1 !important;
    transition-duration: 0.01ms !important;
    scroll-behavior: auto !important;
  }
  .reveal { opacity: 1; transform: none; }
}
```

**这不是可选项** —— 前庭功能障碍用户会因动效产生生理不适。

### 6.3 降级链（最重要的部分）

**崩溃的看板娘比没有看板娘更糟。** 四级降级，任何一环失败都不白屏：

```
① WebGL 不支持        → 静态立绘（SVG），显示提示
② Cubism Core 缺失    → 静态立绘 + console.warn
③ 模型文件 404/解析失败 → 静态立绘 + console.warn
④ 全部成功            → Live2D 交互 + 气泡 + 模型切换器
```

```ts
function webglSupported(): boolean {
  try {
    const c = document.createElement('canvas');
    return !!(c.getContext('webgl2') || c.getContext('webgl'));
  } catch { return false; }
}
```

### 6.4 加载时机：不抢首屏

```ts
function scheduleIdle(fn: () => void) {
  if ('requestIdleCallback' in window) {
    requestIdleCallback(fn, { timeout: 3000 });
  } else {
    setTimeout(fn, 1500);
  }
}
// window.load 之后才 scheduleIdle
```

PixiJS + Live2D 插件加起来约 300 KB。放在首屏加载会让 LCP 明显变差。

### 6.5 性能优化：四条实测有效的

实测环境：2015 款 MacBook Pro（Intel Iris 6100）

| 优化 | 前 FPS | 后 FPS | 内存节省 |
| --- | --- | --- | --- |
| 关闭物理模拟（`physics: false`） | 32 | 58 | −18 MB |
| 贴图 2048 → 1024 | 41 | 52 | −24 MB |
| 精简动作文件（删 `dance_00.mtn`） | 45 | 56 | −8 MB |

**① 空闲帧率限制到 30fps，交互时拉到 60**

```ts
const origMax = app.ticker.maxFPS;
app.ticker.maxFPS = 30;
let interacting = false;
const bump = () => {
  if (interacting) return;
  interacting = true;
  app.ticker.maxFPS = 60;
  setTimeout(() => { app.ticker.maxFPS = origMax; interacting = false; }, 1600);
};
canvas.addEventListener('pointermove', bump, { passive: true });
```

**② 页面隐藏时暂停 Ticker**

```ts
document.addEventListener('visibilitychange', () => {
  if (document.hidden) app.ticker.stop();
  else app.ticker.start();
});
```

**③ 鼠标跟踪只在 canvas 附近监听** —— 看板娘只占右下角一个小方块，
没必要在整个 viewport 上监听 `mousemove`。

**④ 贴图降级** —— 多数低端机 1024 足够。

**⑤ 构建期探测 + tree-shake（最有效的一条）**

Cubism Core 是 Live2D Inc. 的专有软件，**禁止再分发**，
所以绝大多数站点根本没有它。如果不做处理：

1. 每个页面都会刷一条 `404 /models/live2dcubismcore.min.js`；
2. Pixi.js + Cubism4 渲染器（约 **760 KB**）会被打进产物，却永远用不上。

**解法：在 `astro.config.mjs` 里探测文件是否存在，把结果编译成常量。**

```js
// astro.config.mjs
import { existsSync } from 'node:fs';
import { fileURLToPath } from 'node:url';

const PUB = fileURLToPath(new URL('./public/', import.meta.url));
const LIVE2D_ENABLED =
  existsSync(`${PUB}models/live2dcubismcore.min.js`) &&
  existsSync(`${PUB}models/shizuku/shizuku.model3.json`);

export default defineConfig({
  vite: {
    define: {
      __LIVE2D_ENABLED__: JSON.stringify(LIVE2D_ENABLED),
    },
  },
});
```

```ts
// src/env.d.ts
declare const __LIVE2D_ENABLED__: boolean;
```

```ts
// Live2DMascot.astro —— 动态 import 在 if(false) 分支里会被整块 tree-shake
if (!__LIVE2D_ENABLED__) {
  if (fallback) fallback.hidden = false;
  return;
}
const PIXI = await import('pixi.js');
const { Live2DModel } = await import('@jannchie/pixi-live2d-display/cubism4');
```

**实测效果（同一个项目，只改探测逻辑）**：

| | JS 总产物体积 | 主要 chunk |
| --- | --- | --- |
| 无探测（总是打包 Pixi） | **1046 KB** | lib.js 606 KB + cubism4.js 156 KB + ... |
| 有探测（无 Core） | **10 KB** | 全部被 tree-shake |

**减少 99%**。而且双向都验证过：放一个假的 `live2dcubismcore.min.js` 进去，
构建时 Pixi 又会正常被打包 —— 说明这个开关是真开关，不是把功能砍了。

> 组件层面还要同步：`data-enabled="false"` 时不渲染「切换模型」按钮
> （只有一个模型时切换没有意义），并把静态立绘直接设为可见。

### 6.6 移动端适配

```css
.stage canvas { touch-action: none; }   /* 防止滑动页面时误触发 */
```

不加这条，手机上快速滑动会同时触发页面滚动和看板娘点击反馈，体验很碎。

移动端还要缩小尺寸（220×300 → 110×150），并限制物理模拟。
静态立绘在移动端容易压住正文，额外降一档高度并调低不透明度。

### 6.7 常见坑

| 现象 | 原因 | 解法 |
| --- | --- | --- |
| 点一下冒出三句反馈 | 路由切换/热更新时监听器叠加 | 绑定前先 `removeEventListener`，或维护监听器数组在卸载时统一移除 |
| 切换模型时黑屏 1-2 帧 | `destroy()` + `create()` 连续调用被浏览器合并重绘 | 中间加 100ms 延时 |
| 模型位置偏 | 不同模型画布留白不同 | 按内部尺寸算：`scale = (h / 2.2) / model.internalModel.width`，`anchor.set(0.5, 1)` |
| `autoInteract` 不生效 | 指针事件被遮挡 | `canvas` 需要 `pointer-events: auto`，且父容器 `touch-action: none` |

### 6.8 互动设计

```ts
model.on('hit', (hitAreas: string[]) => {
  say(hitAreas.includes('body') ? '唔…被戳到了！' : '在戳我呀？');
});
```

- **说话气泡**：24 条随机台词 + 12 条按时间段的问候语；
- **滚动反应**：滚动时 12% 概率触发吐槽（太频繁会烦）；
- **模型切换**：`⇄` 按钮循环切换，`localStorage` 记住选择；
- **隐藏/唤回**：`localStorage` 持久化；
- **切换时淡入**：切换模型后有 100ms 过渡。

## 7. 背景图片系统

### 7.1 极简风的背景策略：从「全屏特效层」到「每页封面图」

旧版设计用了一个五层全屏背景栈（背景图 + 极光 blob + 粒子网络 + 噪点 + 遮罩）：

```
┌─ L4  可读性遮罩 ──────────── 保证正文可读
├─ L3  噪点纹理 ────────────── 消除渐变色带
├─ L2  粒子网络 (Canvas) ───── 鼠标斥力互动
├─ L1  极光光晕 (CSS blob) ─── 呼吸感光源
└─ L0  背景图片 (用户自定义) ── 个人风格载体
```

这套在玻璃拟态风里成立，但在**等宽极简风里是灾难**：
满屏动画 + 模糊 + 粒子 = 视觉噪音，恰好抵消了极简风要的"安静"。

**新策略**：

| | 旧版 | 新版 |
| --- | --- | --- |
| 背景 | 全屏固定层，5 层叠加 | **每页自己的封面图**，普通页纯白 |
| 特效 | 极光 + 粒子 + 噪点 | 只保留滚动揭示与数字滚动 |
| 强调 | 全站统一 | 首页 / 文章页有封面，列表页留白 |

`Background.astro` 组件被**整体删除**。封面图改为页面自己的元素：

```astro
<!-- src/pages/index.astro -->
<section class="hero-banner">
  <div class="hero-bg"></div>       <!-- background-image: url('/img/bg/hero.svg') -->
  <div class="hero-overlay"></div>   <!-- 亮/暗两套渐变遮罩 -->
  <div class="hero-content">...</div>
</section>

<style>
  .hero-banner { position: relative; min-height: 62vh; overflow: hidden; }
  .hero-bg {
    position: absolute; inset: 0;
    background-image: url('/img/bg/hero.svg');
    background-size: cover;
    transform: scale(1.04);
    transition: transform 1.2s var(--ease-out);
  }
  .hero-banner:hover .hero-bg { transform: scale(1.08); }
</style>
```

### 7.2 替换封面图

把图片放进 `public/img/bg/`，改 `background-image` 路径即可。

**做等宽风格封面图的建议**：参考站的封面是二次元角色图（人物 + 场景），
但对技术博客，更合适的是**代码符号 + 山峦剪影**这种低饱和插画 ——
`public/img/bg/hero.svg` 就是手绘的等宽风：天空渐变、太阳光晕、三层山峦、
小屋、树，以及飘落的 `</>`、`{ }`、`=>`、`fn main() {`、`O(n log n)` 等代码符号。

### 7.3 亮暗主题的适配处理

同一张封面在亮/暗主题下需要不同的遮罩，否则亮色模式文字会看不清：

```css
.hero-overlay {
  background: linear-gradient(180deg,
    rgba(255,255,255,0.35) 0%, rgba(255,255,255,0.15) 45%, rgba(255,255,255,0.75) 100%);
}
html.dark .hero-overlay {
  background: linear-gradient(180deg,
    rgba(20,22,26,0.55) 0%, rgba(20,22,26,0.4) 45%, rgba(20,22,26,0.88) 100%);
}
```

### 7.4 性能注意

- 封面图走 `transform: scale()` 会在 hover 时触发合成层动画，比 `filter: blur()` 便宜得多；
- 背景图建议用 AVIF/WebP + `<picture>` fallback，单张控制在 300 KB 内；
- SVG 封面图（如 `hero.svg` 仅 3.9 KB）是性价比最高的方案 —— 任意分辨率不糊、零请求延迟。

## 8. 文章写作与上传流水线

### 8.1 三条路径并存

```
路径 A（最快）  站内 /write/ 写作台

```

### 8.2 写作台功能清单（已实现）

| 功能 | 说明 |
| --- | --- |
| 表单化元信息 | 标题 / 分类（下拉）/ 日期 / 标签 / 摘要 / 精选 / 草稿 |
| Markdown 编辑器 | 语法高亮（等宽字体）+ 9 个快捷工具按钮 |

### 8.3 frontmatter schema（类型安全）

```ts
const blog = defineCollection({
  loader: glob({ base: './src/content/blog', pattern: '**/*.{md,mdx}' }),
  schema: z.object({
    title: z.string().max(80),
    description: z.string().max(200).optional(),
    pubDate: z.coerce.date(),
    updatedDate: z.coerce.date().optional(),
    heroImage: z.string().optional(),
    tags: z.array(z.string()).default([]),
    category: z.enum(['OI', 'AI', '工程', '随笔', '比赛']).default('随笔'),
    draft: z.boolean().default(false),
    featured: z.boolean().default(false),
    weight: z.number().default(1),
  }),
});
```

**关键点**：schema 在**构建期**校验。字段写错、日期格式不对、分类拼错 —— 直接构建失败，
而不是发到线上才发现。

`z.string().max(80)` 这类约束同样值得加：超长标题会变成构建失败，
而不是几个月后在 Search Console 里才发现 SEO 有问题。

### 8.4 Decap CMS 配置要点

```yaml
backend:
  name: github
  repo: YOUR_USERNAME/oiblog
  branch: main
media_folder: public/img/uploads
public_folder: /img/uploads
publish_mode: editorial_workflow   # 草稿 → 审核 → 发布
```

`editorial_workflow` 让文章走「Draft → In Review → Ready」三态，

- 正文行高 1.85，字号 1.0625rem —— 中文长文最舒服的组合；
- 每篇文章预估阅读时长（中文 400 字/分钟，代码块额外加权）；
- `scroll-padding-top: 6rem` —— 锚点跳转不被顶栏遮住；
- 代码块 `overflow-x: auto` + 悬停显示复制按钮；
- 表格 `display: block` + 横向滚动，窄屏不撑破布局。

## 11. 部署方案

### 11.1 四种选择

| 平台 | 优点 | 缺点 | 适合 |
| --- | --- | --- | --- |
| **Cloudflare Pages** | 免费、全球 CDN、国内访问尚可 | 首次访问略慢 | ✅ **推荐** |
| **Vercel** | 体验最好、零配置 | 免费版有构建限制 | 有海外用户 |
| **GitHub Pages** | 完全免费、仓库即备份 | 国内访问不稳 | 纯练手 |
| **自有服务器** | 完全可控 | 要自己运维 | 有 VPS |

### 11.2 Cloudflare Pages 配置

```
Framework preset:  Astro
Build command:      npm run build
Build output dir:   dist
```

`package.json` 里已经配好 `postbuild: pagefind --site dist`，
所以搜索索引会自动生成，**不需要额外配置**。

### 11.3 GitHub Pages

```js
// astro.config.mjs
export default defineConfig({
  site: 'https://yourname.github.io',
  base: '/your-repo-name',   // ← 必须加
});
```

### 11.4 自有服务器（Nginx）

```nginx
server {
  listen 443 ssl http2;
  server_name blog.example.com;
  root /var/www/blog/dist;

  location / {
    try_files $uri $uri/ $uri/index.html =404;
  }

  # 静态资源长缓存
  location /_astro/ {
    expires 1y;
    add_header Cache-Control "public, immutable";
  }

  gzip on;
  gzip_types text/css application/javascript application/json image/svg+xml;
}
```

**全静态产物，Nginx 不需要 Node 运行时**，运维成本极低。

### 11.5 CI 自动发布

```yaml
# .github/workflows/deploy.yml
name: Deploy
on:
  push:
    branches: [main]
jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with: { node-version: '22.23.4' }
      - run: npm ci
      - run: npm run build
      - uses: actions/upload-pages-artifact@v3
        with: { path: './dist' }
  deploy:
    needs: build
    runs-on: ubuntu-latest
    steps:
      - uses: actions/deploy-pages@v4
```

> **Node 版本必须钉死 `>= 22.23.4`** —— Astro 7 的硬性要求，
> 低于此版本会直接拒绝启动，报错信息还比较隐蔽。

## 13. 踩坑清单（实战沉淀）

### 13.1 Astro 7 专属

| 坑 | 现象 | 解法 |
| --- | --- | --- |
| **配置文件位置** | `src/content/config.ts` 被静默忽略，集合全空 | 必须是 `src/content.config.ts` |
| **zod 导入源** | `import { z } from 'astro:content'` 报错 | 改成 `import { z } from 'astro/zod'` |
| **defineCollection 导入源** | 从 `astro/zod` 导入会报 "not a function" | 它来自 `astro:content` |
| **entry.slug 消失** | 所有 `post.slug` 变 undefined | 改用 `post.id` |
| **render API** | `await post.render()` 失效 | `import { render } from 'astro:content'; await render(post)` |
| **Tailwind 集成方式** | `@astrojs/tailwind` 已移除 | 改用 `@tailwindcss/vite` 插件 + `@import 'tailwindcss'` |
| **markdown 处理器** | remark/rehype 插件不生效 | Astro 7 默认 Sütterlin，需显式 `processor: unified()` |
| **sitemap 拆分** | `sitemap.xml` 404 | 改成 `sitemap-index.xml` |
| **Node 版本** | 直接拒绝启动 | Node ≥ 22.23.4 |
| **端点文件后缀** | `.js` 端点里 `astro:content` 解析失败 | 用 `.ts` |

### 13.2 Astro 模板语法

| 坑 | 现象 | 解法 |
| --- | --- | --- |
| **`<pre>` 里的 JSON** | `Expected '}' but found ':'` | `{` 被当成表达式，用 `set:html={...}` |
| **模板里的 CSS 大括号** | 解析错误 | 同样用 `set:html` 或 `<style>` 块 |

### 13.3 CSS

| 坑 | 现象 | 解法 |
| --- | --- | --- |
| `var(--x / 0.5)` | lightningcss 优化时报 "Unexpected token Delim('/')" | 改用 `color-mix(in oklab, var(--x) 50%, oklch(0 0 0 / 0))` |
| `color-mix` 配 `transparent` | 混合时偏色 | 第二色用 `oklch(0 0 0 / 0)` 明确透明 |
| `@utility` 语法 | Tailwind v3 写法不识别 | v4 用 `@utility name { ... }` |
| **换设计系统后旧变量悬空** | `var(--fg-strong)` 在新 CSS 里不存在 → 回退成无效值，样式碎裂 | 先加兼容别名层（见 [4.6](#46-迁移旧设计的正确姿势)），再逐页重写 |
| **macOS grep 不支持 `\|`** | `grep "a\|b"` 匹配不到任何东西 | BSD grep 用 `-E` 或 `grep -E "a\|b"`；或直接用 ripgrep |

### 13.4 Live2D

见 [6.7 常见坑](#67-常见坑)。

**额外一条（构建期）**：

| 坑 | 现象 | 解法 |
| --- | --- | --- |
| **运行时探测太晚** | 每个页面都请求 `/models/live2dcubismcore.min.js` → 一堆 404 + 760KB Pixi 白进产物 | 构建期探测文件是否存在 → `vite.define` 注入常量 → tree-shake（见 [6.5 ⑤](#65-性能优化四条实测有效的)） |

### 13.5 环境（本机沙箱）

| 坑 | 现象 | 解法 |
| --- | --- | --- |
| **npm 装不存在的版本** | `ETARGET No matching version found for @types/pixi.js@^8.0.0` | PixiJS 8 自带类型，不要装 `@types/pixi.js` |
| **vite 清缓存被拦** | `SAFE_DELETE_BULK_CONFIRM_REQUIRED`，dev server 卡死 | 用 `astro build` + `astro preview` 代替 dev server 做截图验证 |
| **代理拦截本地回环** | `curl http://127.0.0.1:4321` 返回 502 | 加 `--noproxy '*'` |
| **`nohup ... &` 起不来** | 后台进程立刻退出，日志为空 | 用工具的后台任务模式（`run_in_background`）而不是 shell 脱离 |
| **直调 `astro build` 缺步骤** | 搜索 0 条结果 —— Pagefind 索引没生成 | Pagefind 是构建**后**的独立步骤，要走 `npm run build`（含 og + pagefind） |
| **预览服务端口占用** | `Another astro preview server is already running` | `astro preview stop` 后重启；注意它会提示实际端口 |

### 13.6 视觉还原

| 坑 | 现象 | 解法 |
| --- | --- | --- |
| **凭感觉做"像"** | 做完总差一口气：字号、灰度、间距全不对 | 抓参考站 computed style + 下载主题 CSS 读原始规则，把感觉变成数值（见 [4.0](#40-设计语言来源从参考站反推设计-dna)） |
| **只改首页** | 首页像了，列表页/详情页还是旧的 | 全站令牌统一 + 兼容别名兜底 + 逐页重写 |
| **极简风加了粗体** | 层级全靠 bold，视觉变重 | 层级靠字号/颜色/留白/线条；字重只留一处（导航当前项） |

## 一句话总结

> 博客搭建这件事，**内容占 10%，工程占 90%**。
> 真正花时间的从来不是「把页面做出来」，而是：
> 1. 让几百篇文章的首屏都不超过 50 KB；
> 2. 让看板娘在 2015 年的笔记本上不拖垮页面；
> 3. **让写文章这件事的摩擦降到「新建一个 md 文件」那么低。**
>
> 第 3 条最重要。一个博客的成败，取决于**你多久能写完一篇**，而不是首页多好看。
>
> 而"好看"这件事本身，也应该像写代码一样有依据：
> **抓参考站的 computed style，把感觉变成数值**，而不是靠猜。
